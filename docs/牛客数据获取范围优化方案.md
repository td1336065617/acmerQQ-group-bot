# 第一部分　赛程（比赛信息）获取范围

## 1.1 现状与四平台对照（2026-09-18 实测）

| 平台 | 数据源（代码） | 当前"未开始"场次 | 最远一场 | 视野 |
| --- | --- | --- | --- | --- |
| Codeforces | `contest.list` 取 `phase=BEFORE`（`contest_fetcher.py:466`） | 9 | 2026-10-17 | 全部已公布比赛（响应 39KB，2154 条里筛 BEFORE） |

| **牛客** | 日历 API + **当前月/下月** + **名称过滤**（`:493` / `:513`） | 7 | 2026-10-03 | **只有 2 个月，且丢 34% 的真牛客赛事** |

> 赛程链路的抓取、缓存、预热、推送（早报 / 赛前 15 分钟提醒）本身工作正常，本次只改**"取哪些、取多远"**。

## 1.2 问题 A：赛事归属判定写错（主因）

**牛客日历接口的 `ojName` 实际取值**（2025-09 ~ 2026-10 共 14 个月实测）：

| `ojName` | `ojId` | 场次 |
| --- | --- | --- |
| `NowCoder` | 0 | **229** |
| `AtCoder` | 6 | 57 |
| `CodeForces` | 9 | 30 |

**代码现状**（`src/contest_fetcher.py:538`）：

```python
elif platform == "nowcoder":
    if "牛客" not in oj_name and "牛客" not in name:
        continue
```

`"牛客" in "NowCoder"` **恒为 False** → 判定退化成"**比赛名里含牛客**"。

**后果**：14 个月里 229 场 NowCoder 赛事被丢掉 **78 场（34%）**，且分布极不均匀（下表为损耗最明显的月份，完整月份补注在表下）：

| 月份 | 牛客总场 | 旧口径丢弃 | 丢弃占比 |
| --- | --- | --- | --- |
| 2025-11 | 25 | 10 | 40% |
| 2025-12 | 19 | 10 | 53% |
| 2026-03 | 23 | **13** | **57%** |
| 2026-04 | 21 | 12 | 57% |
| 2026-05 | 25 | 11 | 44% |
| 2026-07 | 17 | 6 | 35% |
| 2026-08 | 17 | 4 | 24% |
| 2026-09（当前） | 8 | **0** | 0% |
| 2026-10（当前） | 3 | **0** | 0% |

（未列出的月份：2025-09 为 11 场丢 3、2025-10 为 27 场丢 6、2026-01 为 8 场丢 0、2026-02 为 14 场丢 1、2026-06 为 11 场丢 2）

> 当前月份恰好 0 丢弃 —— 这正是"现网看起来没问题"的原因；一旦进入校赛/新生赛赛季（3~5 月、11~12 月）就会大面积漏。

**被丢弃的都是真牛客赛事**（随机摘录）：
`河南萌新联赛2026第（三）场：郑州轻工业大学`、`第六届上海理工大学ACM程序设计全国挑战赛`、`金山杯2026年武汉理工大学程序设计竞赛`、`新疆大学2025年新生赛(同步赛)`、`苏州工学院（常熟理工学院）2025新生赛（同步赛）`、`大连大学2025年11月程序设计竞赛(同步赛)`、`武汉工程大学第八届ACM新生赛(同步赛)`、`中国地质大学（武汉）2025年冬新生赛（同步赛）`、`2025年华南理工大学程序设计竞赛（秋季赛）`、`汤圆头 Round 1`。

**性质**：该过滤的**本意**是把日历里混排的 AtCoder 比赛分出去（AtCoder 自 1.1.1 起已改用官网源），并非要排除校赛 → **属于判定口径写错，不是产品取舍**。

## 1.3 问题 B：时间窗只有"当前月 + 下月"

- 日历按自然月返回：请求 `month=YYYY-M` 得到该月全部比赛（含已结束的）。
- 实测今天只有 `2026-09`（12 场，8 牛客 + 4 AtCoder）与 `2026-10`（3 场国庆集训派对）有数据，`2026-11` 起为空 → 牛客当前最多提前约 **1 个月**排期。
- 但**系列赛会整季提前排**：`2026牛客暑期多校训练营 1~10` 横跨 7 月（1-5）与 8 月（6-10）；`2026牛客国庆集训派对 day1~3` 在 9 月中旬已可查到。只抓 2 个月时，6 月只能看到 7 月那 5 场多校，8 月 5 场要等 7 月才出现；寒假算法基础集训营同理。
- 成本极低：日历单次请求 0.6~1.5KB（gzip），多抓 3 个月约 +3KB/次刷新。

## 1.4 问题 C：洛谷隐含 20 条/页上限（当前不漏，属保险项）

- 实测 `luogu.com.cn/contest/list` 页内 `lentille-context`：`perPage = 20`、`count = 1371`、`result` 只有 20 条；排序为**开始时间倒序**（实测：10-04 → 10-02 → 10-01 → 09-27 …）。
- 因为倒序，**全部未来赛事必然落在第 1 页**（当前 8 场）→ 现在不是缺陷。
- 但只要未来赛事数超过 20 场就会开始漏，加一个 3~5 行的翻页保险：`len(result) == perPage` 且最后一条 `startTime` 仍在未来 → 继续取第 2 页（最多 3 页）合并去重。

## 1.5 问题 D：`_fetch_nc_month` 的 AtCoder 死分支（卫生问题）

`_fetch_nowcoder_calendar` 只以 `platform="nowcoder"` 调用（`contest_fetcher.py:177`），1.1.1 起 AtCoder 走官网，因此 `_fetch_nc_month` 里的 atcoder 分支已不可达。本次保留"OJ 判定函数支持 atcoder"的能力（未来可复用），但把注释写明它是**牛客取数器**，避免后人误解为 AtCoder 仍有双源。

## 1.6 优化设计

### A. 赛事归属改为按 OJ 身份判定

新增 `_nc_platform_of_item(item) -> str | None`：

```python
oj = str(item.get("ojName") or "").strip().lower()
name = str(item.get("contestName") or "")
if "nowcoder" in oj or "牛客" in oj:
    return "nowcoder"
if "atcoder" in oj:
    return "atcoder"
if "codeforces" in oj:
    return None                      # 交给 CF 官方 API（数据更全）
# ojName 缺失/改版时回退比赛名，保留旧行为作为兜底
if "牛客" in name:
    return "nowcoder"
if "atcoder" in name.lower():
    return "atcoder"
return None
```

**效果**：牛客赛程 = 日历里**全部 NowCoder 赛事**（系列赛 + 高校校赛/新生赛同步赛 + 集训营/多校 + 自主创建赛），与 CF / AtCoder / 洛谷"不做名称过滤"的口径一致。

### B. 滚动月份窗口 + 并发 + 分级容错

```python
NC_MONTH_LOOKAHEAD = 3        # 当前月 ~ +3 月；0 = 恢复"只抓当前月"
NC_REQUIRED_MONTHS = 2        # 必需月：当前月、下月（与现状保证一致）
```

- 新增纯函数 `_nc_months(now, lookahead)`：生成月份列表并处理跨年（2026-12 → 2026-12、2027-1、2027-2、2027-3）；
- `asyncio.gather` 并发取各月（单请求 ~1KB）；
- **必需月失败 → 抛错**，沿用既有 `_fallback_to_stale_cache` 旧缓存兜底（与现状语义完全一致）；
- **更远月份（+2、+3）尽力而为**：单月失败只打 warning，用已取到的月份（避免远期空月份的一次抖动导致整个牛客刷新失败）；
- 合并沿用 `contest_id` 去重、按开始时间排序；
- 新增一行统计日志，便于以后核对口径：
  `牛客日历 2026-09~2026-12 共 41 场（保留 33：NowCoder 33 / 过滤其他 OJ 8）`

### C. 洛谷翻页保险

`_fetch_luogu` 增加：`len(rows) == perPage` 且末条仍在未来 → 取 `page=2`（最多 3 页）合并去重；其余逻辑不变。

### D. 清理 AtCoder 死分支注释

只改注释与函数 docstring，不改行为。

### E. 噪音控制开关（**待你确认**）

放宽后，早报（今日比赛）、`nk比赛` / `最近nk比赛`、`最近比赛` 汇总、**赛前 15 分钟提醒**（`src/scheduler.py:184`）都会覆盖高校校赛 / 新生赛同步赛 / 自主创建赛。

- 日历接口**没有赛事分类字段**，无法精确区分"系列赛 / 校赛 / 自主创建赛"，所以开关只能是两种口径：
  - `all`（**默认，推荐**）：按 OJ 归属，全部牛客赛事；
  - `series_only`：仅比赛名含"牛客"（= 现状口径）。
- 落地：`settings["nowcoder_scope"]` + `main.py` 配置校验 + `pages/settings/index.html` 下拉 + README/CONFIG 说明（约 0.3 天）。
- 若你不想要新配置项：固定为 `all`，只在常量处留注释，§1.6 E 整条跳过。

# 第二部分　资料卡（牛客）数据获取范围

## 2.1 三处上限（代码位置）

```
详细资料请求
   └─ analysis 缓存（12h）
        └─ 练习记录扫描         ← 上限①：20 页 × 100 条 = 2000 条   ← 用户实际观察到的问题
             └─ 汇总「已通过题」集合
                  └─ 逐题抓题目元数据（难度 / 知识点）
                                    ← 上限②：只抓 300 道题，每题 1 次 10.9KB 请求
        └─ Rating 历史解析      ← 上限③：只保留最近 200 场（同一请求内截断，牛客未触顶）
```

| # | 位置 | 代码 | 现状 |
| --- | --- | --- | --- |
| ① | `src/account_fetcher.py:81-82` | `NOWCODER_ANALYSIS_PAGE_SIZE = 100`<br>`NOWCODER_ANALYSIS_MAX_PAGES = 20` | 练习记录最多 2000 条 |
| ② | `src/account_fetcher.py:83` | `NOWCODER_PROBLEM_META_LIMIT = 300` | 难度/知识点只覆盖 300 道通过题 |

## 2.2 牛客接口能力的实测边界

| 项 | 实测结论 |
| --- | --- |
| 练习页 `pageSize` | **服务端上限 200**（`201/250/300/500` 返回 200 但内容为 `pageSize is too big :300`，0 数据行） |
| 练习页分页信息 | `<ul data-total="N">` 的 N = **当前 pageSize 下的总页数**；不足一页时该属性不存在（此时应按 1 页） |
| 练习页行数 | `pageSize=200` 时首页返回 200 行；提交数 = 页面状态里的「次提交」 |
| 练习页体积 | `pageSize=100` 解压 106KB / 传输 14.0KB；`pageSize=200` 解压 186KB / 传输 **19.9KB**（gzip，aiohttp 默认接受） |
| 题库 JSON 接口 | `GET /acm/problem/list/json?keyword=&pageSize=50&page=N`，无需 Cookie/XHR 头；返回 `problemCount` + `problemSets[]`（含 `difficulty`、`tagList`） |
| 题库 JSON `pageSize` | **上限 50**（100 直接报 `pageSize is too big :100`） |
| 题库规模 | `problemCount = 14446` → 50 条/页 ＝ **289 页**（`ceil(14446/50)`）；单页传输 8.8KB（解压 80KB），全库 ≈ **2.5MB 传输 / 23MB 解压**（实测整库构建 35.8 秒，索引落盘 0.72MB） |
| 题库 JSON 难度口径 | 存在 `difficulty ∈ {1,2,3,4,5,-1}` 的**未评定哨兵值**：同一题在现有 HTML 列表页里难度单元格为**空**（现有解析 → `None` → 「未标难度」）。真实难度从 400 起 |
| 题库 JSON 知识点 | `tagList[].name` 与现有 HTML `tag-label` **同源**（抽题对照：`枚举/排序`、`暴力`、`图论/连通性` 一致） |
| 单题查询体积 | JSON `keyword=<id>`：解压 1KB / 传输 **0.5KB**；现有 HTML 搜索页：解压 41KB / 传输 **10.9KB**（21 倍） |
| 稳定性 | 偶发 chunked 截断（`IncompleteRead`），依赖现有 `fetch_text_with_retry` 重试；索引构建需容忍单页失败 |

## 2.3 用户侧影响（真实账号抽样）

| 账号 | 练习提交 | 页面状态 | 现状读到 | 症状 |
| --- | --- | --- | --- | --- |
| `738977420` | 3816 | 39 页 @100 | **2000/3816（52%）** | `complete=False` → **AC 率不显示**、难度分布缺一半 |
| `886965097` | 1346 | 7 页 @200 | 1346/1346 ✅ | 通过 473 题，但**只有 300 题拿到难度** → 173 题堆进「未标难度」 |
| 牛客 Rating 榜 #1-50（抽样 45） | 最高 3816 | 20 页 @200 | — | — |
| 牛客 Rating 榜 #51-90（抽样 40） | 最高 6015；**7.5% 超过 2000 条** | — | — | 该区间约每 13 人就有 1 人卡片被截断 |

> 结论：2000 条上限不是理论问题，而是**约 5%~10% 的活跃牛客用户**会触发；20000 条上限实测样本中无人触达，作为兜底足够。

## 2.4 目标口径

| 维度 | 目标 |
| --- | --- |
| 练习记录 | 最多 **100 页 × 200 条 = 20000 条**（与 AtCoder 20000 对齐）；按用户实际提交数取页，不做无谓翻页 |
| AC 率 | 实际读取量 ≥ min(提交数, 20000) 且无分页失败 → 正常展示 |
| 题目难度/知识点 | **覆盖题库列表中的全部通过题**（不再 300 截断）：由「按需逐题抓」改为「题库索引本地查表」；题库外的比赛题牛客未公开难度，如实计入“未标难度” |
| 最高 Rating | 不再受 200 场历史窗口影响 |
| 成本 | 稳态网络开销**不高于**现状（见 §2.6） |
| 兼容 | 卡片排版、指令、缓存键全部不变；失败时逐级降级，不出现空白卡片 |

## 2.5 实现设计

### 2.5.1 练习记录扫描（上限①）

```python
NOWCODER_ANALYSIS_PAGE_SIZE = 200            # 原 100；实测服务端上限
NOWCODER_ANALYSIS_SCAN_LIMIT = 20000         # 新增：条数上限（对齐 AtCoder 20000）
NOWCODER_ANALYSIS_MAX_PAGES = NOWCODER_ANALYSIS_SCAN_LIMIT // NOWCODER_ANALYSIS_PAGE_SIZE   # = 100
NOWCODER_ANALYSIS_PAGE_INTERVAL = 0.15       # 新增：页间节流（照 AtCoder 做法，可设 0 关闭）
```

**页数计算**（纯函数，便于单测）

```
pages_needed(submission_count, data_total, page_size, max_pages):
    total = submission_count                                   # 首页状态「次提交」
    if total is None: total = (data_total or 1) * page_size    # 回退：用分页总页数
    return clamp(ceil(total / page_size), 1, max_pages)
```

- 首页必须成功（沿用现状：失败即 `AccountFetchError`，卡片保留基础资料与 Rating 历史）；
- 其余页并发抓取，信号量沿用 `6`，每页后 `sleep(PAGE_INTERVAL)`；
- **空页提前终止**：任一页解析出 0 行 → 停止后续页（隐私/空练习账户不再空转 100 次请求）；
- 单页失败不中断：记录 `pages_missing`，合并已有行。

**完整性判定**（替换现有 `complete`，`account_fetcher.py:1968`）

```python
expected_rows = min(submission_count or len(rows), NOWCODER_ANALYSIS_SCAN_LIMIT)
complete = (len(rows) >= expected_rows) and not pages_missing
```

- `acceptance_rate`、`accepted_submission_count` 仍只在 `complete` 时给出；
- 覆盖率文案三态：
  - 完整：`练习页读取 3816/3816 条提交；题目元数据 1106/1106`
  - 触顶：`练习页读取 20000/26114 条提交（最多读取 20000 条 / 100 页）`
  - 部分失败：`…（部分分页读取失败）`

**兜底 guard**：若首页在 `pageSize=200` 下解析出 0 行且无状态数据（对端收紧了上限），自动用 `pageSize=100` 重试一次并打 warning。

**内存**：20000 行 × 约 200B ≈ 4MB/次；分析信号量为 2（`:312`）→ 峰值约 8MB。

### 2.5.2 题目元数据：题库索引（上限②）

**目标**：把「每题 1 次 10.9KB 的 HTML 搜索」换成「一次全库抓取 + 本地查表」，从而取消 300 题上限。

```python
NOWCODER_PROBLEM_LIST_JSON_URL = "https://ac.nowcoder.com/acm/problem/list/json"
NOWCODER_PROBLEM_INDEX_PAGE_SIZE = 50        # 服务端上限
NOWCODER_PROBLEM_INDEX_CONCURRENCY = 6
NOWCODER_PROBLEM_INDEX_TTL = 7 * 24 * 3600   # 难度/知识点几乎不变
NOWCODER_PROBLEM_META_FALLBACK_LIMIT = 300   # 仅索引不可用时的降级上限（原 300 常量的语义）
```

**索引结构**（只保留分析需要的字段）

```python
{"<problem_id>": {"d": 1500, "t": ["图论", "连通性"]}}   # d=None 表示未评定
```

- 全库 14446 题 → 精简后约 **0.6MB**（实测单题 47B，落盘 0.72MB）；
- 落盘位置与 SQLite 同目录：`default_store_path().parent / "nowcoder_problem_index.json"`（即 AstrBot 数据目录 `plugin_data/acmer_qq_group_bot/`，`ACMER_STORE_DIR` 可覆盖），构造参数可注入路径以便单测；格式 `{"version": 1, "fetched_at": ..., "problems": {...}}`，原子写，与 `contest_cache.json` 同风格；
- 重启直接加载，不重爬；`version` 不匹配或条目数异常（< 5000）则忽略并重建。

**构建流程**

1. 先取 `page=1` 拿 `problemCount` → `pages = ceil(problemCount / 50)`（14446 → 289 页）；
2. 其余页并发（信号量 6）抓取，单页失败重试 1 次后跳过；
3. **缺页率 > 10% 视为构建失败**：不写盘、保留旧索引；
4. 解析：`difficulty < 400 → None`（对齐现有 HTML 空单元格口径）；`tags = [t["name"] for t in tagList]`，去重去空。

**触发时机**

- 主路径：`scheduler.tick()`（`src/scheduler.py:53`）新增一次「索引巡检」——仅索引缺失/过期时构建，5 分钟退避起、最长 1 小时（照 `_record_warm_failure` 写法），single-flight（`asyncio.Lock`）；
- 卡片路径**不做同步全库抓取**：索引不可用时走 §2.5.3 的降级。

**查询路径**

```
索引已加载 → 本地字典查找（0 网络请求，覆盖题库列表中的全部通过题）
索引未命中（新题/不在题库里的比赛题）→ 限额单题 JSON 查询（0.5KB）→ 结果写回索引
  · 单次分析最多补查 100 道（NOWCODER_PROBLEM_META_LOOKUP_LIMIT），避免为查不到的题白等
  · 题库列表明确没有的题（比赛题/定制自测题）记入负缓存（随索引落盘），后续不再补查
  · 关键词只命中"另一道题"时不采纳，避免张冠李戴给出错误难度
索引整体不可用 → 单题查询，最多 FALLBACK_LIMIT=300 题（= 现状行为）
```

**函数清单（新增/改动，均在 `src/account_fetcher.py`）**

### 2.5.4 Rating 历史窗口（上限③，零成本；与"20 页"问题无因果）

**实测现状**：牛客评级榜 Top25 的 `allRatedCount` 最大仅 **50 场**（示例账号 36 场），远小于 200 → **牛客当前并未被这个窗口截断**，它不是用户反馈的 20 页问题的一部分。

| 平台 | 最高 Rating 来源 | 是否受 200 场窗口影响 |
| --- | --- | --- |
| Codeforces | API `user.info.maxRating`（`:1152`） | ❌ 不受影响（历史列表/趋势图受） |
| AtCoder | 用户页 `highest` 字段（`:2654`） | ❌ 不受影响（历史列表/趋势图受） |
| 牛客 | **由历史推导** `max(rating)`（`:1581`） | ✅ 受影响（当前未触顶） |
| 洛谷 | **由 elo 历史推导**（`:2169` / `:2286`） | ✅ 受影响 |

**改动**：`RATING_HISTORY_LIMIT: 200 → 1000`。四个平台的历史本来就在**同一次请求**里返回（`_parse_nowcoder_history` 的 `rows[-200:]`、`_parse_cf_history(limit=…)`、AtCoder / 洛谷同款），截断只发生在解析阶段 → **零网络成本**。

- 收益：牛客/洛谷的「最高 Rating / 最高段位」不再可能遗漏早于 200 场的峰值；CF/AtCoder 历史更完整；
- 卡片趋势图仍按 `RATING_CHART_DISPLAY_LIMIT` 取点，**排版不变**；记忆量 ≈ 200KB/账号；
- 若要严格隔离到牛客，可另设 `NOWCODER_RATING_HISTORY_LIMIT`；推荐**统一 1000**。

### 8.3 与方案的偏差（据实修正）

1. **题库页数**：方案写“≈290 页”，实际 `ceil(14446/50) = 289` 页。
2. **索引体积**：方案估“≈0.6MB”，实测落盘 0.72MB。
3. **“覆盖全部通过题”需限定为“题库列表中的通过题”**：牛客题库列表只有 14446 题，
   只存在于比赛中的题目（如 `255137` 一类定制自测题）题库列表页与 JSON 接口都查不到，
   页面本身也不暴露难度/知识点 → 这 321 道只能计入“未标难度”。
   为此新增两项保护：单次分析补查上限 100 道 + “确认不在题库”的负缓存（随索引落盘）。
4. **`difficulty < 400` 归为未评定**：与现有 HTML 口径一致（题库列表页同题难度单元格为空），
   因此 `tests/test_accounts.py` 的合成用例把难度 `3` 改为 `800` 以匹配真实数据。
