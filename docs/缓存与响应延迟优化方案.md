# acmerQQ群机器人 缓存与响应延迟完整优化方案

> 版本：v1（2026-09-08）
> 基线：acmer_qq_group_bot v1.3.2（生产已部署）
> 前提：AstrBot 单实例单账号、多群、单群成员上限约 2000、4C4G Ubuntu
> 目标：消除"请求时卡一下"的周期性延迟；让缓存从"被动过期"变为"主动预热"
> 约束：用户可见功能与文案不变；force 路径仍然即时

---

## 一、现状：缓存全景与问题定位

### 1.1 当前各层缓存

| 层 | 存储 | TTL | 过期后行为 | 刷新方式 |
| --- | --- | --- | --- | --- |
| 比赛数据 | 内存 + `data/contest_cache.json` | 在线 5 分钟 / 线下 30 分钟 | 请求时同步抓取（single-flight） | **被动** |
| 账号摘要资料 | 内存 + SQLite `profile_cache` | 10 分钟 | 请求时同步抓取 | **被动** |
| 账号详细资料 | 同上 | 10 分钟 | 请求时同步抓取 | **被动** |
| 重型分析 | 内存 + SQLite | 12 小时 | 请求时同步抓取 | **被动** |
| 题目资源 | 内存 | 24 小时 | 请求时同步抓取 | **被动** |
| 排行快照 | SQLite `rank_snapshot` | 60 分钟 | 先返回旧快照 + 后台刷新 | 半自动（SWR） |
| 排行内存缓存 | 内存 `_rank_cache` | 5 分钟 | 请求时同步全群计算 | **被动** |
| 本周进步榜(progress) | 无快照 | — | **每次请求同步全群计算** | **无缓存** |
| 图片渲染 | `data/output_cache/response-{digest}.png` | 按内容 digest | 内容变化才重渲染 | **被动** |
| 渲染器/字体探测 | 无 | — | 每次渲染重跑 `which`/`fc-match` | **每次重探测** |

### 1.2 问题清单

**P1 周期性卡顿（最主要）**
- 比赛数据 5 分钟 TTL 一过，**第一个请求的用户要同步等抓取**（4 平台 + 线下赛）。
- 没有任何后台预刷新，缓存只在被请求时才更新 → 每 5 分钟必有一个用户卡。

**P2 排行双轨 TTL 打架**
- `rank_snapshot` 60 分钟（SWR）与 `_rank_cache` 5 分钟并存；
- `_rank_cache` 过期后走同步全群计算，快照的 SWR 收益被抵消。

**P3 本周进步榜无缓存**
- `progress` 模式完全绕过 `rank_snapshot`（表无 progress 维度），每次请求同步全群抓取；
- 洛谷用实时排名 `-rank` 作指标，需 7 天基线；当前快照历史不足 7 天 → delta 恒为 None。

**P4 渲染冷启动慢**
- 首次渲染要起浏览器（30s 超时）或 Pillow；
- 渲染器/字体探测每次重跑（`fc-match` 子进程最长 5s）；
- 渲染失败无短时负缓存（menu_navigation 有，acmer 无）。

**P5 无缓存淘汰与预热策略**
- 输出图片缓存按 digest 永不过期，磁盘单调增长；
- 没有"热点数据预热"概念（哪些群/哪些平台该提前刷）。

## 二、目标架构：三级缓存 + 主动预热

```
                  ┌─────────────────────────────────────────┐
   用户请求 ─────▶│ L1 内存缓存（进程内，最快，秒级 TTL）      │
                  │ 比赛/资料/排行/渲染探测结果               │
                  └───────────────┬─────────────────────────┘
                                  │ miss / 过期
                                  ▼
                  ┌─────────────────────────────────────────┐
                  │ L2 持久缓存（SQLite / JSON 文件）         │
                  │ profile_cache / rank_snapshot / contest  │
                  │ 支持 stale-while-revalidate              │
                  └───────────────┬─────────────────────────┘
                                  │ 需要新鲜
                                  ▼
                  ┌─────────────────────────────────────────┐
                  │ L3 远端抓取（OJ 接口，single-flight）      │
                  │ 限速 / 负缓存 / 熔断 / 失败兜底           │
                  └─────────────────────────────────────────┘

         ▲ 主动预热（新增）
         │
   ┌─────┴──────────────────────────────────────────────┐
   │ BackgroundWarmer（挂在现有 PushScheduler 上）        │
   │  · TTL 到期前 60~90s 预刷新比赛数据                  │
   │  · 按活跃度排序预热群排行快照                         │
   │  · 周期清理：过期缓存行、旧渲染图片、负缓存            │
   │  · 有界并发（全局 semaphore），不与用户请求抢资源      │
   └────────────────────────────────────────────────────┘
```

**核心原则**：用户请求永远尽量命中 L1/L2；L3 抓取由后台在 TTL 到期前完成。

## 三、具体改造项

### O1【P1 高收益】比赛数据主动预热（预期消除 90% 周期性卡顿）

- 位置：`src/scheduler.py` tick + `src/contest_fetcher.py`
- 做法：
  - 给 `ContestFetcher` 增加 `async def warm(platforms)`：对**即将过期**（剩余 TTL < 预热窗口，默认 90 秒）的平台执行 `fetch_platform`，命中 single-flight，不阻塞用户请求。
  - scheduler 每个 tick（30 秒）调用一次 warm；每 tick 最多预热 1 个平台，避免突发流量。
  - 预热失败不重试风暴：失败后按平台退避（已有 `_fallback_to_stale_cache` 兜底）。
- 影响：用户请求命中热缓存，不再等待抓取。
- 风险：低（只是把原本用户触发的抓取挪到后台）。
- 注意：线下赛 TTL 30 分钟，预热窗口相应放宽到 5 分钟。

### O2【P2 高收益】统一排行缓存 TTL

- 位置：`main.py` `RANK_CACHE_TTL=5*60`、`src/rank_service.py`
- 做法：
  - 让 `rank_service.read()` 在 store 可用时**一律走快照**，不再回退到 `_collect_rank_rows` 的 5 分钟内存缓存（快照没有才同步算）。
  - `_rank_cache` 仅作为 "无 SQLite 模式"（`ACMER_STORE_BACKEND=kv`）的兼容路径。
- 影响：群排行固定在 60 分钟新鲜窗口 + SWR，不会每 5 分钟同步全群算一次。
- 风险：中（要保证 store 不可用时行为不变）。

### O3【P3 中收益】本周进步榜纳入快照 ✅ 已实现

- 位置：`account_store` 新增 `progress_snapshot` / `progress_meta` 两张独立表
  （SQLite 不支持 ALTER PRIMARY KEY，独立表对现有库零风险），
  `rank_service` 通过 `mode="rank"/"progress"` 复用同一套读写与 SWR 逻辑。
- 新鲜窗口：rank 60 分钟；progress **2 小时**（7 天聚合指标，变化更慢）。
- 标脏：绑定/解绑/改名会把 rank 与 progress 一起标脏。
- 后台刷新：`refresh_stale` 分别扫描两种 meta；progress 只对“曾被查询过”
  的群生效，不会为全量群做昂贵的进步榜重算。
- 洛谷专项（已确认可接受）：明确指标优先级 Elo > 排名；把两种 key 统一成
  `luogu`，内部记录 `metric_kind`（elo/rank），避免 key 跳变断基线；
  无 Elo 时用排名变化表示进步，并注明“基于平台排名变化”。
  > 注：洛谷快照历史满 7 天后才会有非空 delta。

### O4【P4 中收益】渲染性能与稳定性

- 位置：`src/output_renderer.py`、`src/account_cards.py`
- 做法：
  1. **进程级缓存渲染器探测结果与字体路径**（`lru_cache` 或带 TTL 的模块级缓存），避免每次渲染跑 `which`/`fc-match`；
  2. **渲染失败短时负缓存**（如 300 秒内同渲染栈直接返回 None 走文字，参照 menu_navigation 的 `RENDER_FAILURE_COOLDOWN`）；
  3. **PNG 有效性校验**（魔数），避免坏图被当成功；
  4. 渲染并发上限已在 v1.3.1 引入（`RENDER_MAX_CONCURRENCY=1`），保持。
- 风险：低。

### O5【P5 低收益】缓存清理与容量控制

- `output_cache/` / `account_cards/` 按 mtime + 总容量清理（如保留最近 200 张或 ≤200MB）；
- `profile_cache` / `fetch_failures` 过期行已在 scheduler 定期清理（已实现，可复核）；
- 负缓存表加条目上限。

### O6【P4 辅助】scheduler 任务不阻塞主循环

- 现状：`tick()` 内联执行 prune/flush/refresh_stale/（新增 warm），群多时可能超过 30 秒周期。
- 做法：把重任务放到独立 task（`asyncio.create_task`）并加锁防重入，tick 只负责调度。
- 风险：低。

## 五、不建议改动

1. 不引入 Redis/消息队列（单机单进程，SQLite + 内存足够）。
2. 不把比赛 TTL 拉长到 10 分钟以上（比赛数据时效性敏感）。
3. 不改"绑定验证码 10 分钟 / 快照 90 条上限"等既有语义。
4. 不为预热开辟无界并发（会打爆 OJ 与自身 CPU）。
5. 不改用户可见文案（洛谷"基于排名"提示需你确认是否可加）。

## 六、评审结论（已确认）

1. 比赛预热窗口：**TTL 到期前 90 秒**后台预热（TTL 5 分钟）✅
2. 洛谷无 Elo 时：**接受用"平台排名变化"表示进步**，并在展示上注明 ✅
3. 渲染图片缓存清理：**按总容量 500MB** 上限清理（LRU，保留最新）✅

## 七、实施顺序

O1（比赛预热）→ O4（渲染优化）→ O2（排行统一）→ O3（进步榜快照）→ O5/O6（收尾）
