## 1. 新发现（v2 漏掉的）

### ⓪ 牛客/洛谷绑定「编辑」必失败（严重）
- 现象：编辑一个牛客或洛谷的绑定（哪怕只想改昵称）→ 保存报错"请填数字 UID 或主页链接"
- 证据链
  1. 线上 120 条绑定中，`handle != platform_user_id` 的有 **32 条，且只出现在 luogu(14) 与 nowcoder(18)** —— 即这两个平台的绑定 **100%** 命中：
     `nowcoder: handle='td1336065617', platform_user_id='645160704'`；`luogu: handle='td1336065617', platform_user_id='273293'`
  2. 前端编辑态回填的是 `item.handle`（`index.html:971`）—— 对牛客/洛谷是**展示名**，不是账号标识
  3. 实测归一化：`normalize_account_identifier("nowcoder","td1336065617") -> ''`、`("luogu","td1336065617") -> ''`（而传入 `'645160704'` / `'273293'` / 主页链接 → 正常）
  4. 后端遇空即拒：`main.py:5735-5738` → `error_response(invalid_identifier_message)`
- 影响：牛客/洛谷绑定**无法通过后台编辑**（除非管理员自己知道并手填 UID 或主页链接）
- 修法：编辑态回填 `platform_user_id`（列表接口已返回该字段：`main.py:5659-5662`）；UI 上加显示名提示，例如
  `账号：645160704（展示名：td1336065617）`
- 验收：编辑一个牛客绑定只改昵称 → 保存成功且账号标识不变

### ⓪b 理论风险：编辑可能**静默改错账号**
- 若某用户的展示名恰好是**纯数字**、且该数字正好是**另一个真实 UID**，则归一化会成功 → 编辑保存会把绑定指向别人的账号
- 线上实测：`handle 为纯数字且 ≠ platform_user_id 的行数 = 0` → **当前 0 例，风险未发生**
- 但修 ⓪ 的同一个改动（后端"同账号则跳过归一化校验"）可以顺带**彻底消除**该风险，因此建议一并做

### ⑥ 「已换绑，替换原账号 X」误报（100% 触发）
- 证据：`main.py:5752-5761` 无条件读取 `old_handle`；`main.py:5794` `"replaced": old_handle or None`；前端 `index.html:1008` 只要 `replaced` 非空就提示"已换绑"
- 现象：编辑任意已存在绑定（哪怕只改昵称、账号没动）都会弹出"已换绑，替换原账号 <同一个账号>"
- 修法：仅当 `old_handle.casefold() != profile.handle.casefold()` 时才置 `replaced`
- 验收：只改昵称 → 提示"绑定已保存"；真正换账号 → 提示"已换绑，替换原账号 X"

## 2. 对 v2 两处结论的更正

| v2 的说法 | 实际 | 影响 |
| --- | --- | --- |
| "② 锁死平台/QQ 后，想改打错的 QQ 要先删再加，**群资格记录会丢**" | **错**。`remove_binding_atomic` 只删 `accounts`（与 pending），**不碰** `group_members` 与 `rank_member_overrides`（`account_store.py:552-566 / 567+`） | 锁死的代价≈0，② 可为纯前端一行；v2 的顾虑不成立 |
| "② 严重度=中" | 线上无任何证据（见下），触发条件苛刻 | 降级为 P5 |

**"线上无证据"的判定依据**：120 条绑定里没有"同一 user 在同一平台重复"（PK 限制不可能），也没有出现"同一人多平台但 handle 与本人其他平台不一致"的异常聚集；同一人跨平台同名（7 例）是**正常用法**（同一 handle 在两个平台是不同账号）—— 我 v1/v2 把它算不上问题 ✓。

## 3. 排除的假阳性（这次专门核查过的）

| 怀疑 | 结论 | 依据 |
| --- | --- | --- |
| 深链 `#/bindings` 会让「归属群」下拉为空 | **不成立** | `boot()` 无条件先 `loadConfig()`（`index.html:1482-1487`），而 `loadConfig` 会 `fillGroupSelectors()`（`index.html:1310`） |
| 同一 handle 出现在两个平台 = 幽灵绑定 | **不是问题** | 不同平台是不同账号，"同名绑定"是常见合法用法（线上 7 例） |
| ④ 归属群覆盖用户「退出排行」= 需要修 | **数据支持不修** | 线上 `group_members.enabled=0` 的行数 **= 0**，即从来没人用过"退出排行"，覆盖行为零实际影响 |

## 4. 逐条修法（更新版）

### ⓪ + ③（合并处理，P1）
1. **前端**：编辑态 `#bfIdentifier` 回填 `item.platform_user_id || item.handle`；并在字段下显示展示名提示
2. **后端**（save 分支，抓取之前）：
   `same = 记录存在 and normalized == record["platform_user_id"].casefold()`
   - `same` → 跳过归一化失败判断与 `get_profile`，沿用现有 `handle/platform_user_id/display_name/profile_url`，只更新 `qq_name`（与群语义）
   - 不 `same` → 保留现状（归一化 + 抓取 + 唯一性校验）
3. 说明：`platform_user_id` 线上**无空值**（0/120），比较可靠；仍保留 `handle` 兜底以防个别平台缺字段

### ⑥（P2）后端一行
### ①（P3）
- 前端：编辑态下拉默认项文案改为「保持不变（不改成员资格）」，值仍为空串（后端 `if group_id:` 天然不动成员资格）
- 可选增强：`GET bindings` 条目带 `groups`（新增 `account_store.get_groups_for_users(user_ids)` 一次批量 SQL）→ 抽屉里显示"当前已在：群A(自然)、群B(强制)"。**若想再省，可砍掉这条，只留默认项改名**
### ⑤（P4）
- 前端轻量归一化后比较：`trim → 取最后一个 '/' 之后片段 → toLowerCase` vs `existing.platform_user_id.toLowerCase()`
### ②（P5）
- 前端：编辑态 `#bfUser` 设 `readonly`、`#bfPlatform` 设 `disabled`，加提示"如需更换请删除后重新新增"
- 附带更正：删除只删绑定行，群资格与"排行成员"记录都不受影响，重新新增即可恢复

## 10. 追加：1.19.2 的职责归位（用户决策）

**决策（用户）**：归属群本质是为排行榜服务，账号绑定页与「排行成员」重复 → **新增绑定时可设置**，**编辑与展示落在排行榜管理**。

**落地**
- 抽屉的「归属群」：**仅新增态显示**（编辑态隐藏）；绑定列表去掉「归属群」列
- 新增时选的群 → 改走 `add_rank_member(added_by="webui:binding")`（覆盖表）：在「排行成员」里是"强制加入"、可移除并还原，与手动强制加入同一份数据
- 编辑绑定不再携带 `group_id` → 编辑不会扰动成员资格
- 群内自助/代绑定的 `group_id`（自动加入发起群排行）**保持不动**——那是用户/管理员在群里绑定时的设计意图
- `GET bindings` 的 `groups` 字段保留（供将来做筛选；当前 UI 不用，1ms 成本）

### 10.1 追加调整（1.19.3，按用户反馈）

- 新增绑定时选的归属群**改回老路径**（`save_binding(group_id=…)` → 普通加入 `enabled=1`）：这是"管理员顺手加入"，用户可在群里「退出排行」自行退出；不再写覆盖表，响应去掉 `membership_added`。
- 需要"强制 + 留痕"的成员仍统一走「群排行 → 排行成员」（覆盖表、可识别来源、移除时按 `preexisting` 还原）。
- 保持：抽屉「归属群」仅新增态可见；列表不展示归属群；编辑不携带 `group_id`。
- 已知取舍（接受）：新增时选群会覆盖用户此前的「退出排行」（老路径 `DO UPDATE SET enabled=1`）——线上 `enabled=0` 行数为 0，实际影响为零。

### 10.2 决策 B（1.19.4）：把“人 → 群”视图补回来

**背景纠正**：1.19.2 把绑定页的归属群“展示”一并删掉时删过头了 —— 那个展示是**唯一**能看到“某人在哪些群有排行资格”的地方。

**关系（代码证据）**：`group_members(enabled=1)` ∪ `rank_member_overrides` 同时是
- 归属群（`GET bindings` 的 `groups`，人 → 群）
- 排行榜成员集（群 → 人，再 `JOIN accounts ON platform` 才进具体榜单）

**方案 B（用户选定）**
- 保留接口字段 `groups`
- **编辑抽屉**加**只读**提示：`当前已在：群A（自然成员）、群B（强制加入）（查看与调整请在「群排行 → 排行成员」）`
- 列表**不加列**；设置仍只在**新增**时可选
- 结果：群→人 / 人→群 两个视角互补，且“设置”不重复
