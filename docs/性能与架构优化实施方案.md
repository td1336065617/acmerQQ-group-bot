# acmerQQ群机器人：绑定-OJ-衍生功能 性能与架构优化实施方案

> 状态：设计稿（已按评审结论更新，待进入实现）
> 基线：插件 v1.2.28（当前工作区代码）
> 部署前提：AstrBot **单实例 / 单机器人账号**，一个进程服务所有群；多群，单群成员上限约 2000；
> 周活跃约 1000 人、周消息约 2 万。
> 本次文档只做方案设计，不改代码。
>
> **评审结论（已确认）**
> - 单实例单账号；多群；生产环境已有真实绑定/排行数据，**需要迁移保留**。
> - 数据更新敏感度低：各 OJ 的 Rating 约一天变化 1~2 次，做题数略快但也不需要高敏感度。
>   因此默认新鲜窗口：**OJ 资料 30 分钟、排行快照 60 分钟**（可配置），force 路径仍即时抓取。
> - SQLite 文件位置（`data/plugin_data/acmer_qq_group_bot/`）可以。
> - **不新增任何必须安装的第三方依赖**：存储层用 Python 标准库 `sqlite3`；
>   `aiosqlite` 仅在环境已安装时作为可选加速，不作为 requirements 依赖，保证即插即用。

---

## 1. 目标

1. 消除"群排行 / 我的战绩 / 绑定后相关查询"在**用户请求路径上同步等待全群/全平台爬取**。
2. 避免"重启即冷 + 5/10 分钟缓存错位 + 缓存 key 重复"造成的**反复爬同一批 OJ 数据**。
3. 在 4C4G 单机、单进程约束下，把账号、排行、快照数据从 AstrBot KV 整表 JSON 迁到
   **本地 SQLite（WAL）**，提供索引、事务和可迁移/可回滚能力。
4. 保持所有**用户可见功能与文案不变**；唯一接受的语义调整：排行/个人卡排行部分改为
   **stale-while-revalidate**（有旧快照时先返回，后台刷新；首次无快照才等待）；
   并按评审放宽为：普通查询默认展示约 30 分钟内的资料、约 60 分钟内的排行快照即可，force 仍即时。

## 2. 行为不变清单（红线）

以下任何一项都不允许因重构而变化：

- 绑定流程：`绑定xx <账号>` → 验证码追加到平台公开资料字段 → `确认绑定xx` → 绑定成功；
  验证码 10 分钟有效、只存哈希；同一 OJ 账号只能属于一个 QQ 用户。
- 群归属：群内绑定成功自动加入**发起绑定群**的排行；私聊绑定后需在目标群发
  `加入群排行`；`退出群排行` 后不再展示；`preserve_opt_out` 语义保留。
- 排行规则：按平台分开、不跨平台比 Rating；`群x排行` 每页 30 人、可翻页；
  `群排行`/`本周进步榜` 只展示各平台 Top5；洛谷无 Elo 时按公开排名排序；
  昵称显示规则（qq_name → display_name → user_id）不变。
- `我的账号`/`我的cf` 等个人卡的字段、图表、数据源标注不缩水；分析结果 12h、题目资源 24h 的缓存口径不变。
- `刷新我的战绩`、`update`、WebUI 测试推送的 **force 语义**不变。
- 定时推送：早报每日一次/群；赛前 15 分钟提醒去重键必须带群 ID；@全体降级逻辑不变。
- Codeforces 2.1s 请求间隔、50 人批量上限、分析并发 2、牛客题目元数据并发 6 等**平台保护参数**不放松。
- 资料"新鲜窗口"默认可放宽到 **30 分钟**、排行快照 **60 分钟**（评测结论：Rating 一天变化 1~2 次，
  做题数略快但不需要高敏感度）；`force` 路径（刷新我的战绩/update/绑定校验）仍然即时。

## 4. 目标架构

```
QQ 消息 / WebUI
     │
     ▼
┌──────────────────────────────────────────────┐
│ main.py（指令分发保持现状，逐条小改）           │
│ 绑定 / 解绑 / 我的战绩 / 群排行 / 加入退出 …   │
└──────┬──────────────────────────┬─────────────┘
       ▼                          ▼
┌────────────────┐      ┌─────────────────────┐
│ AccountStore   │      │ ProfileService      │
│ (SQLite WAL)   │◄────►│ (持久化缓存+单飞)    │
│ accounts/      │      │ 负缓存/熔断/分析队列 │
│ members/pending│      └──────────┬──────────┘
│ history/cache/ │                 │ 刷新任务
│ rank_snapshot  │                 ▼
└──────┬─────────┘      ┌─────────────────────┐
       │                │ BackgroundWorker    │
       ▼                │ 每(OJ)限速/有界队列  │
┌─────────────────┐     │ 排行物化/快照写入    │
│ RankService     │◄────│ profile 刷新/分析    │
│ 读物化快照       │     │ 缓存清理/指标快照    │
│ stale+后台刷新   │     └─────────────────────┘
└─────────────────┘
       ▼
  RenderQueue（全局渲染 Semaphore 1~2）
```

读路径分层原则：

- **绑定/资料写** → AccountStore 事务；
- **个人卡/群排行读** → 先读本地（profile_cache / rank_snapshot），不足才触发后台刷新；
- **force 路径** → 仍同步等刷新，但底层请求走同一套单飞/限速，不再有重复风暴。

## 6. 存储层实现细节（AccountStore）

### 6.1 数据库位置与连接

- 路径：使用 AstrBot 官方数据目录，保证升级/重装插件不丢数据：

```python
# 参考 来只清楚bot/_resolve_data_dir 的写法
from astrbot.core.utils.astrbot_path import get_astrbot_data_path

def _store_dir() -> Path:
    base = Path(get_astrbot_data_path())      # 异常时回退 Path("data")
    return base / "plugin_data" / "acmer_qq_group_bot"

DB_PATH = _store_dir() / "acmer_store.db"
```

- 连接（**零新增依赖**）：默认用标准库 `sqlite3`，推荐两种实现之一：
  1. **写连接单线程模型（推荐）**：后台启动一个专用线程持有唯一写连接（`threading.Thread` +
     `queue.Queue` 提交写任务），事件循环侧用 `asyncio.to_thread` 提交；读操作走短连接线程池
     （WAL 支持并发读）。所有写操作天然串行，无需 `asyncio.Lock`。
  2. **短连接模型（更简单）**：所有操作 `asyncio.to_thread(sqlite3.connect, path)`，单次操作
     开/关连接，配合 WAL + `busy_timeout`；20k 消息/周量级下开销可忽略，缺点是每次多一次连接建立。
- 若环境已安装 `aiosqlite`，可选用其作为可选加速实现（运行时探测 import），**不进 requirements**。
- PRAGMA：`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON`。

### 6.5 AccountRegistry 重写要点

`account_registry.py` 现有方法**保持同名同参**，内部改为调用 `AccountStore`，这样 `main.py`
绝大多数调用点不用改：

- `get_all_accounts()`：保留实现（SQLite `SELECT *` 或内存缓存），但只用于兼容旧调用；
  新代码路径改走 `get_group_platform_accounts(group_id, platform)` 避免全表读。
- `save_binding` 的"同平台账号已被他人绑定"检查：交给 `uq_accounts_platform_handle`
  唯一索引 + 捕获 IntegrityError，避免全表遍历。
- `record_ratings`：在一个事务内完成"查最后一条 → 决定是否插入 → 清理超 90 条"。
- `get_weekly_deltas`：只对请求的 (user, platform) 对做 SQL 查询，不再读全量。

### 6.6 KV 双写与迁移

发布策略（建议）：
1. 新版本首次初始化：`meta.schema_version` 为空 → 从 KV 读三个大 key，写 JSON 备份到
   `_store_dir()/migration_backup_<ts>.json`，逐表插入并做**数量校验**。
2. 迁移期（默认 1 个版本）：写操作同时写 SQLite 和 KV（KV 写失败仅告警，不阻断）；
   读操作以 SQLite 为主，SQLite 异常时回退 KV。
3. 稳定后版本：`dual_write_kv` 默认关闭，读/写都只用 SQLite。
4. 回滚：保留旧插件文件 + 提供内部命令/入口 `从备份 JSON 恢复 KV`；恢复前必须停机或接受短暂不一致。

## 7. 抓取与缓存层实现细节

### 7.1 持久化 profile_cache

- 序列化：`AccountProfile.public_dict()`（**不包含 verification_value，避免把用户追加的验证码明文入库**），
  恢复时 `AccountProfile(**payload)`。
- kind：
  - `basic`：`detail=False` 的摘要资料（排行用）；
  - `detail`：个人卡的基础详细资料（不含重型分析）；
  - `analysis`：重型分析结果（难度/知识点/语言等）。
- TTL 默认值按"低敏感度"评审调整：
  - `basic`（摘要/排行指标）：默认 **30 分钟**（旧 10 分钟；Rating 一天才变 1~2 次）；
  - `detail`（个人卡基础资料，含做题数等）：默认 **30 分钟**，如实测做题数变化频繁可单独调到 15 分钟；
  - `analysis`：保持 12h；资源类：保持 24h；
  - **缓存落库**，重启不冷；force 路径绕过缓存。
- 读路径：内存 LRU → profile_cache → 网络。
- 写路径：网络成功 → 写内存 + 写库；失败 → 写 `fetch_failures`。

### 7.2 ProfileService 单飞与 stale

```python
class ProfileService:
    def __init__(self, fetcher, cache: ProfileCacheStore, worker, policy): ...

    async def get_profile(self, platform, identifier, *, detail=False, force=False,
                          include_submissions=True,
                          include_difficulty=False, include_analysis=False) -> AccountProfile:
        # force=True：绕过缓存（绑定/刷新我的战绩用），保持现语义
        # force=False：
        #   命中有效缓存 → 返回
        #   命中过期缓存 → 返回 stale 并后台刷新（除非调用方 allow_stale=False）
        #   miss → 单飞抓取
```

- 单飞：进程内维护 `pending: dict[key, asyncio.Future]`，同 key 并发只抓一次。
- 后台刷新任务：由 BackgroundWorker 执行，带**任务去重**（同 key 只有一个 pending）。
- 负缓存：`fetch_failures` 存 `(platform, handle_norm, kind, reason, temporary, expires_at)`；
  永久性失败（账号不存在/格式错）TTL 5min；临时失败（网络/超时）TTL 2min。
- 熔断：连续失败 3 次的 (platform, handle) 在短窗口内直接返回上一次错误文案，不重抓。

### 7.3 CF 批量失败修复

- `get_profiles` 按 50 人 chunk 调 `user.info`；**失败只对当前 chunk 逐账号回退**，
  已成功的 chunk 结果直接写入缓存；
- 失败账号写入负缓存；不再 `main.py:1727-1744` 那种"清空 resolved、全组逐账号重抓"。

### 7.4 OJ 保护参数集中到 `oj_policy.py`

| 平台 | 限制 | 说明 |
| --- | --- | --- |
| codeforces | 批量 50、请求间隔 ≥2.1s | 保留现参数 |
| 通用 | profile 并发 8、analysis 并发 2 | 全局共享，跨群公平 |
| 牛客/洛谷/AtCoder | 每域 QPS 限速（如 2 req/s，可调） | 防止群 A 刷新打爆后群 B 全部超时 |
| 全部 | 每个平台单飞 key | 已实现，保持 |

## 8. RankService 与后台刷新

### 8.1 读路径（stale-while-revalidate）

```
RankService.read(group_id, platform, *, progress=False, allow_stale=True)
  1. SELECT rank_snapshot WHERE group_id/platform
  2. meta = rank_meta 该行
  3. 有快照 且 now - refreshed_at <= RANK_FRESH_SECONDS(默认 3600 = 60 分钟)
        → 返回 rows（秒级）
  4. 有快照 但过期
        → allow_stale=True：返回旧 rows；标记 dirty；入队刷新
        → allow_stale=False（force/首次）：等待本次刷新完成
  5. 无快照
        → 入队刷新并等待（冷路径；完成前不返回空）
```

### 8.2 刷新任务算法

```python
async def refresh_group_platform(group_id, platform, *, progress=False, force=False):
    # 同 (group, platform) 单飞
    members = store.get_group_platform_accounts(group_id, platform)   # 只读该群该平台
    profiles = await profile_service.get_many_basic(platform, handles)
    rows = build_rows(profiles, progress=progress)                    # 复用现有排序逻辑
    await store.replace_rank_snapshot(group_id, platform, rows)       # 事务内 DELETE+INSERT
    await store.record_ratings(entries)                               # 同一批指标
    await store.touch_rank_meta(group_id, platform)
```

- 事件触发：绑定/解绑/加入/退出/昵称更新/账号资料成功刷新 → `mark_dirty(group, platform)`；
- 周期兜底：worker 每 60s 扫 `rank_meta` 中 `now-refreshed_at > 3600s`（60 分钟）且群仍活跃的条目；
  "活跃" = 近 24h 内收到过群消息 **或** 24h 内有人查过该群排行（避免为长期无人查询的群白刷）；
- 公平性：一个 2000 人群占住全局并发时，其他群会被饿死。实现上：
  - 每平台最多 1 个 in-flight，全局并发预算分平台（如 8 个总请求槽）；
  - 队列轮询多个群，单群单轮最多刷新 1 个平台；
  - 或简化：in-flight 上限 = 群数上限（例如 4 个并发 group-platform 任务），配合每平台限速。

### 8.3 个人卡中的群排行

`我的战绩`/`我的cf` 里的"本群第 N 名"不再走 `_load_group_rank_summary` 全群现算，改为：

```
RankService.read(group_id, platform, allow_stale=True)
    然后在 rows 里二分/顺序找 user_id 的名次
```

### 8.4 force 语义

- `update`（比赛数据）与账号无关，保持现有强制刷新比赛缓存逻辑；
- `刷新我的战绩`：对个人资料 force=True 同步重抓；群排行行仍然读快照或 force 该平台一次；
- WebUI"测试推送"：保持现有行为。

### 8.5 单实例告警（可选加固，防 OpenClaw/手工误启第二个 AstrBot）

生产出现过 OpenClaw 残留实例导致的"双 AstrBot 同写 data_v4.db"事故。acmer 侧可做低成本加固：

- 插件初始化时对 `acmer_store.db` 执行 `BEGIN EXCLUSIVE` 短探测或使用文件锁（`fcntl.flock` 非阻塞）；
- 探测到已被其他进程持有 → `logger.warning` 输出醒目告警（提示存在重复 AstrBot 实例），**不阻断插件加载**，避免二次实例把 acmer 存储写坏；
- 不主动退出/杀进程（无权假设哪个实例该留）。

## 12. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 迁移丢数据 | 先备份 JSON；逐表数量校验；双写一版；保留旧插件可直接回滚 |
| SQLite 写锁/阻塞 | WAL + busy_timeout + 专用写线程/短连接模型 + 写操作短事务 |
| stale 数据被用户误认为不更新 | 已确认低敏感度（资料 30 分钟 / 排行快照 60 分钟）；如需可在回复中带"数据更新于 HH:MM"（属新文案，另行确认） |
| 后台刷新与 force 冲突 | force 等待/抢占同 key 任务；任务带 generation，旧任务结果不覆盖新 force 结果 |
| 大群刷新期间多群排队过久 | 每群每平台 in-flight + 全局并发预算 + 平台限速；单群先刷新"最近有查询的群" |
| 零依赖存储实现并发/锁问题 | 标准库 sqlite3 本身线程安全限制由"专用写线程/短连接"规避；不做跨进程假设（已确认单实例） |
