# 第一部分　acmer_qq_group_bot

## A1 赛后赛果推送（第 1 批）

### A1.1 目标与价值

现状只有"赛前 15 分钟提醒"（`src/scheduler.py:204 _maybe_remind`）与早报，比赛结束后没有反馈闭环。补上"赛后赛果"后，群里会自然出现"这场谁打得最好"的话题——这是提升活跃度最直接的一环。

**卡面只放"名次类"信息，不放任何 Rating 变化**（原因见 §A1.2）：

```
🏁 Codeforces Round 1121 (Div. 2) 赛果
本群 4 人参赛 · 赛后 12 分钟
─────────────────────────────
#120  张三 (zhangsan)   6 题   AK
#431  李四 (lisi)       4 题
#890  王五 (wangwu)     3 题
#1520 赵六 (zhaoliu)    2 题
─────────────────────────────
📌 重测中，名次可能微调 · 未通过：D、F
📚 数据源：Codeforces 官方 standings
ℹ️ 评分变化以平台为准

（牛客同款卡面：`#1/1273 · 13/13 题`，数据源标注"牛客个人参赛记录"）
```

### A1.2 **为什么不带 Rating 变化**（评审结论）

| 平台 | Rating 何时更新（评审确认） |
| --- | --- |
| **牛客** | **固定次日 00:00 统一更新**（用户实测） |
| **Codeforces** | **系统重测（system test）完成后**才结算，繁忙场次可达数小时 |
| AtCoder | 相对快，但 `IsRated` 可能延后/为 false |
| 洛谷 | Elo 更新在赛后，可能更久 |

结论：**等 Rating 就等于把推送推迟到几小时甚至第二天，失去时效性**。因此：

1. 赛后 **`settle_delay_minutes`（默认 10 分钟）一次性推送"名次版"**；
2. **不轮询、不等待、不补推评分版**（删掉原方案的"就绪状态机 / 退避探测 / 两级幂等键"）；
3. 卡片**不含 ±分、不含新 Rating**；想看分数变化的成员自己去平台看；
4. 若日后确实想要"评分变化"（例如牛客次日 00:00 后补一条），作为**独立需求**另评估，本期不做（见 §C5）。

### A1.3 触发与幂等（简单版）

挂载点：`PushScheduler.tick()`（`src/scheduler.py:53`，30 秒一次），新增 `_maybe_push_settlements(now, platform_cache)`：

```
每群（group.enabled 且 group.settle_push_enabled）
  └─ 对该群 push_platforms 中的平台 p
       └─ contests = await fetcher.fetch_platform(p)          # 复用 5 分钟缓存
            └─ 候选：c.end_time 存在（缺失则用 start_time + duration_minutes）
                     且 now - c.end_time ∈ [settle_delay_minutes, +2h]
                 └─ 幂等键 settle_<群ID>_<平台>_<contestID>（KV，与 morning_* 同范式）
                      ├─ 已推送 → 跳过
                      └─ 未推送 → 取赛果 → 有人参赛才推 → 成功写幂等键
```

- 单级幂等键，**一场比赛每个群只推一次**；
- `+2h` 窗口保证"比赛结束后才启动插件/重启"的场景也能补推（重启不丢）；
- 赛果数据进程内缓存 6 小时，多群只抓一次；
- 抓不到赛果（接口未就绪/失败）→ 不写幂等键，下一 tick 重试；超过 `+2h` 窗口仍未成功 → 放弃并记日志（避免把过期赛果推到群里）。

### A1.4 赛果数据可得性（2026-09-18 实测）

| 平台 | 名次来源 | 通过题数 | 实测 |
| --- | --- | --- | --- |
| **Codeforces** | `contest.standings?contestId=<id>` | ✅ `problemResults` 里 `points > 0` 计数 | **必须只带 `contestId`**（带 `from/count/showUnofficial` 会报错：`standings for non-admin users are available only via anonymous GET requests with no extra parameters`）；实测单场 **248KB / 9.9 秒 / 6243 行**，行含 `party/rank/points/problemResults` |
| **AtCoder** | `contests/<slug>/results/json` 的 `Place` | ⚠️ 无题目级结果（`standings/json` 与 `/standings` 均**跳转登录页**）→ 用 kenkoooo 提交接口按 `problem_id` 前缀（= 比赛 slug）统计赛时 AC，插件已有该接口 | 实测 `results/json` 8090 行、含 `Place/Affiliation/Competitions/IsRated` 等 |
| **牛客** | ✅ **个人主页接口（已调研完成，推荐主源）**：`/acm-heavy/acm/contest/profile/contest-joined-history?uid=<uid>&page=1&onlyJoinedFilter=true&searchContestName=&onlyRatingFilter=false&contestEndFilter=true`（**未登录可访问**，1~3KB/人）→ 每行直接给 `rank` / `userCount` / `acceptedCount` / `problemCount` | ✅ `acceptedCount` / `problemCount` | 见下方"牛客调研结论" |
| **洛谷** | ❌ 计分板接口需登录（实测 `contest/<id>/scoreboard` → **401 没有权限请求此资源**） | ❌ | 只能确认"是否参赛" |

**牛客调研结论（2026-09-18，浏览器 + 抓包 + 未登录复测）**

两个候选源，**选个人主页接口**：

| 源 | 接口 | 实测返回 | 结论 |
| --- | --- | --- | --- |
| **个人主页参赛记录**（✅ 采用） | `/acm-heavy/acm/contest/profile/contest-joined-history` | 每行 `contestId/contestName/startTime/endTime/rank/userCount/acceptedCount/problemCount/rating/changeValue/ratingStatus`；实测样例：`2026牛客暑期多校训练营10 · rank 1/1273 · ac 13/13 · 4017 (+9)`；未评分场次（`ratingStatus=NO`、`changeValue=0`）**同样有 rank/ac` | **名次与评分解耦** → 不必等次日 00:00 的评分更新；每成员 1 次小请求；按 `contestId` 精确匹配 |
| 比赛页榜单 | `/acm/contest/rank/submit-list?currentContestId=<id>&contestList=<id>` | 全站参赛名单（uid/name/school）+ 题目（index/score/title）+ 每人每题最佳提交；**没有现成名次**（名次由前端按赛制计算：周赛/ACM/OI 规则不同） | 不用于名次；可作为"补题列"或"参赛校验"的辅助源（119KB/场） |

**三个必须记住的实现细节（踩过的坑）**
1. 路径必须带 **`/acm-heavy/`** 前缀；同名 `/acm/...` 路径（插件里已有的 `NOWCODER_CONTEST_HISTORY_URL`）返回的 `dataList` **不含 rank/ac 字段**（第一轮就是这样踩空的）；
2. 未登录可用，但需要 `X-Requested-With: XMLHttpRequest` 与 `Referer: .../acm/contest/profile/<uid>`（沿用插件现有请求头风格）；
3. `contestEndFilter=true` 只返回**已结束**比赛，默认 10 行/页（重用户 30~121 场，只需 page=1，最新在前），并支持 `searchContestName=<比赛名>` 精确定位。

**降级策略（务实）**

| 平台 | 有赛果时 | 无赛果时 |
| --- | --- | --- |
| CF | 名次 + 通过题数 + 未通过题（A5） | 只推"参赛名单 + 比赛链接" |
| AtCoder | 名次（+ 可选的 kenkoooo 通过题数） | 同上 |
| 牛客 | **名次 + 通过题数**（`rank/userCount/acceptedCount/problemCount`） | 同上 |
| 洛谷 | — | 同上 |

> 文案必须写明数据口径（`数据源：Codeforces 官方 standings` / `牛客名次以官方页面为准`），避免用户以为插件漏了信息。**不含评分变化的说明**也放在卡片底部一行：`评分变化以平台为准（牛客次日 00:00 更新）`。

| --- | --- |
| 赛果接口暂未就绪 | 不写幂等键，下一 tick 重试；超过 `+2h` 窗口放弃并记日志 |
| CF standings 报错 | 只用 `contestId` 参数重试一次（这是实测的必要条件）；仍失败 → 推"参赛名单版" |
| 平台名次不可得（**仅洛谷**） | 推"参赛名单 + 比赛链接"，note 标明"名次以官方页面为准"（牛客已可给名次，见 §A1.4） |
| AtCoder 无题目级结果 | 只显示名次；可选用 kenkoooo 补通过题数，失败则该列留空 |
| 部分平台失败 | 逐平台独立推送，成功的平台照常 |
| 渲染失败 | 纯文本兜底 |
| 群会话未就绪 | 沿用 `_group_scene_ready` 跳过（与早报一致） |
| 比赛取消/延期 | `end_time` 缺失或异常时用 `start_time + duration_minutes`；仍异常则跳过并记日志 |

### A1.9 测试（约 12 例）

候选判定（赛后 10 分钟进入、超过 2h 不再补推、`end_time` 缺失用 duration 推算）、单级幂等（同群同场只推一次）、多群共享一次抓取、CF `standings` **只带 contestId** 的参数断言、CF `PRELIMINARY` → 卡片带"重测中"note、`solved` 计数（`points > 0`）、AtCoder `Place` 匹配、名次不可得时降级为参赛名单、无人参赛不推送、专用卡 HTML/Pillow 双路径产图、`CARD_FORMAT_VERSION` 提升后缓存未命中、渲染失败回退文字。

### A1.10 工作量与风险

约 **1.5 天**（比原方案少 1 天：去掉了就绪状态机与轮询）。风险：

## A2 每日一题 / 推荐补题（第 2 批）

### A2.1 目标与价值

把刚落地的**牛客题库索引**（14446 题、难度 + 知识点、本地查表零请求）变成"每天都会用"的功能：

1. **每日一题**（群维度）：早报末尾附 1 题，或随时用 `每日一题` 查看当天题目；
2. **推荐补题**（个人维度）：在 `我的战绩 详细` / `查询牛客 <uid> 详细` 的卡片里给 3 道"该练的题"。

### A2.2 抽题与推荐规则

**每日一题（群维度）**
- 难度锚点：取本群已绑定成员在牛客评级的中位数为基准；映射表 `CF/牛客 Rating → 题目难度`（如 Rating 1200 → 难度 1000~1400），取该区间；
- 知识点轮换：按"星期几 % 知识点清单"轮换（避免天天数学），知识点取自索引里出现频次 Top-N；
- 稳定性：同一天同群同一题 → KV `daily_<群ID>_<YYYYMMDD>` 记录题号；编号用"当天种子 = hash(群ID + 日期)"在候选集内取模，**不依赖随机数**，保证可复现；
- 排除项：群内已有成员**已通过**的题（若索引里有该成员已通过集合，见 A2.3）。

**推荐补题（个人维度）**
1. 从分析结果拿：`difficulty_distribution`（已有）、`category_distribution`（牛客/AtCoder 有）、`solved_problem_ids`（**需新增**，见 A2.3）；
2. 取"难度在个人中位档 ±1 档、知识点属于个人薄弱 Top3、且不在已通过集合里"的题，按 (难度升序, 知识点覆盖) 排前 3；
3. 输出：`题目名 · 难度 · 知识点 · 链接`（牛客链接 `https://ac.nowcoder.com/acm/problem/<id>`）。

```sql
ALTER TABLE mod_events ADD COLUMN appeal_by   TEXT;    -- 处理人（webui:<user> / qq:<openid>）
```

## B3 竞赛域名白名单（第 3 批，跨插件联动）

### B3.1 问题

`src/rules.py:35-40` 的 `LINK_RE` **只做存在性判断**（`:1227-1229`），命中即 `has_link=True` 并加 25 分；插件**没有任何域名维度的白名单**（四类豁免都是"人"或平台侧策略）。ACM 群日常刷 `ac.nowcoder.com` / `codeforces.com` / `atcoder.jp` / `luogu.com.cn` 链接，配合"召唤式引流/私聊引流"模板，很可能被判"值得送审"甚至处置。

### B3.2 设计

1. **域名抽取**：新增 `src/links.py`：

   ```python
   URL_RE = re.compile(r"(?:https?://)?((?:[a-z0-9-]+\.)+[a-z]{2,})(?::\d+)?", re.I)
   def extract_domains(text: str) -> set[str]: ...   # 小写、去端口、去掉 www. 归一
   ```
   （写法可参考 `src/normalize.py:396 digits_of` 的纯正则抽取风格；`LINK_RE` 现有的短链/裸域名也要覆盖。）
2. **配置**：`domain_allowlist`（默认预置：`ac.nowcoder.com`、`nowcoder.com`、`codeforces.com`、`atcoder.jp`、`luogu.com.cn`、`luogu.com`、`xcpc.link`、`xcpc.ink`、`vjudge.net`、`codechef.com`、`icpc.global`、`hdu.edu.cn`）；`domain_allowlist_enabled`（默认开）；WebUI 可编辑（**记得同步 `pages/manage/app.js` payload**）。
3. **命中逻辑**（已拍板：**只降权，不豁免**）：
   - 在 `main.py:923` 前计算 `allowlisted = 消息中所有域名 ∈ 白名单`；
   - 把 `allowlisted` 传入 `rules.evaluate()`，在 `src/rules.py:1280-1282` 处对 `has_link` 做处理：白名单内 → 不计 25 分且不置 `has_link`；
   - 混入任一非白名单链接 → 仍按"有链接"处理（保守）；

## C5 数据就绪结论（已确认）

**问题**：牛客的"名次"是否在比赛结束后**立刻**可得（评分已知要等次日 00:00）。

**结论：名次赛后即可得，不需要等评分。** 依据两条：

1. **结构性依据（实测）**：`/acm-heavy/acm/contest/profile/contest-joined-history` 的 `rank` / `userCount` /
   `acceptedCount` / `problemCount` 与评分字段**完全解耦**——实测 `ratingStatus=NO`、`changeValue=0`
   （即评分尚未结算）的比赛**同样有 rank 与通过题数**；
2. **使用侧确认**：牛客名次在比赛结束后即可在比赛页/个人主页查看（用户确认）。

**因此定稿**：`settle_delay_minutes` 默认 **10 分钟**（赛后即可拿到名次，无需等待评分）；
2 小时补推窗口仅用于"插件重启/接口抖动"场景。若某场确实取不到（例如个人记录未公开），
按既有降级走"参赛名单版"（比赛页 `submit-list` 的 `signUpUsers`）。
