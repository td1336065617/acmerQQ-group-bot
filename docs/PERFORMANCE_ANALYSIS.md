# acmerQQ群机器人 性能瓶颈与优化方向分析报告

> 分析范围：`acmer_qq_group_bot` 插件（v1.2.27）
> 基本原则：**保留现有全部功能**（指令、数据源、绑定验证、卡片/长消息渲染、定时推送、WebUI 配置均不变），只从**算法与架构**角度提出优化方向。
> 文中行号对应本仓库当前代码，便于定位。

---

## 一、现状架构速览

```
QQ 消息 → on_message/on_group_message（单进程 asyncio 事件循环）
                │
                ├─ ContestFetcher  比赛抓取（aiohttp 单会话，内存+磁盘缓存，并发合并）
                ├─ AccountFetcher  账号资料抓取（aiohttp + CF 全局限速锁 + 内存缓存）
                ├─ AccountRegistry 账号/群排行/快照（AstrBot KV，整对象读改写）
                ├─ PushScheduler   每 30s 后台任务（早报 + 赛前 15 分钟提醒）
                └─ Renderer        AdaptiveOutputRenderer / AccountCardRenderer
                                   （HTML→headless 浏览器 / Pillow，全局线程锁）
```

整体设计已经做了很多正确的事：单 `aiohttp.ClientSession` 复用 TCP 连接、比赛抓取有“并发请求合并 + 过期缓存兜底”、排行有 5 分钟短缓存、CF 摘要走 `user.info` 批量接口、渲染放 `asyncio.to_thread`。瓶颈集中在**规模增长后的串行化、全量读写和重计算**上。

---

## 二、瓶颈分析（按影响从高到低）

### B1. Codeforces 全局限速锁把“详情/排行”完全串行化

**位置**：`src/account_fetcher.py:63`（`CF_MIN_REQUEST_INTERVAL=2.1`）、`:298`（`self._cf_lock`）、`:628-634`（每次请求前全局 sleep）。

- 所有 CF 请求（`user.info` / `user.rating` / `user.status`）共用一把**进程级互斥锁**，任意两次请求至少间隔 2.1 秒。
- `user.info` 已批量（50 handle/次，`get_profiles`），**但 `user.rating`、`user.status` 只能单 handle**。
- 后果示例：
  - `本周进步榜`（progress 模式）对每个成员走 `get_profile(detail=True)`（`main.py:1756`），CF 成员每人要 3 次 CF 请求（info+rating+status），一次 200 人的进步榜冷缓存计算 ≈ 200×3×2.1s ≈ **21 分钟**（被锁完全串行，且期间任何“我的cf”查询都要排队）。
  - `我的cf` 单次详情 ≈ 3×2.1s ≈ 6.3s + 网络，体感明显。
- 这是当前**最大的单点瓶颈**：并发不存在，规模越大越糟。

### B2. 群排行每次按“群×平台”全量重算，且与“个人战绩”的排行查询互不共享

**位置**：`main.py:1632-1919`、`:1696-1919`。

- 缓存键包含 `(group, platform, progress, record_metrics)`（`main.py:1640-1644`）。`record_metrics` 不同就**分开缓存、重复计算**：同一群同一平台，`群排行`（记录快照）与 `@某人 战绩`（只读）会各算一遍完整榜单。
- `_load_group_rank_summary`（`main.py:933-985`）为了给“我的战绩”显示一个“本群第 N 名”，会触发**整个群该平台的全量成员抓取**。每次个人查战绩的代价 = 一次群排行计算的代价。
- 没有“平台级”全局榜单：同一个用户在不同群重复抓取/解析（虽然 profile 有 10 分钟内存缓存，但 `get_all_accounts()`、成员遍历、快照写入仍每群重复）。
- progress 模式对非 CF 平台也走 `detail=True`，为了一张“近 7 日变化”表去抓全部提交/难度分析这类重型数据（12h 缓存也挡不住冷启动）。

### B3. KV 存储“整对象读改写”，快照写入放大严重

**位置**：`src/account_registry.py` 全文件；`main.py:1819-1843`。

- AstrBot KV 每次 `get_kv_data`/`put_kv_data` 都是整块读写。现状：
  - `get_all_accounts()`：每次排行都读回**全部用户全部平台**的账号表（O(总绑定数)）。
  - `record_ratings()`：每次群排行（`record_metrics=True`）都先读回**全部快照**，追加后**整体写回**。快照每用户每平台保留 90 条（`history[-90:]`）。1000 用户 × 4 平台 = 36 万条记录的对象每次排行都序列化一次。
  - `save_binding()` 要全表扫描去重；`get_weekly_deltas()` 每次读回整张快照表。
- 后果：排行延迟被 KV 读写放大；快照表持续增长且无 TTL 清理；大群场景下 KV 读写时间可能超过网络抓取时间。

### B4. 渲染：进程级浏览器每次冷启动 + 全局锁串行 + 同步头像下载

**位置**：`src/output_renderer.py:93`（`_render_lock`）、`:124-161`（整个渲染持锁）、`:422`（`subprocess.run`）；`src/account_cards.py:684`、`:919-966`、`:1175-1186`。

- **全局锁**：`AdaptiveOutputRenderer.render()` 从“检查缓存→写 HTML→启动浏览器→截图”全程持有唯一一把锁；`AccountCardRenderer._render()` 同理。长消息转图、个人战绩卡、群排行卡之间**完全互斥排队**，多个群同时触发高并发时形成队列；单张卡片冷渲染 1~5s，队尾可能等几十秒。
- **浏览器每次渲染都重新拉起 headless Chromium/Firefox**（`subprocess.run`，30s 超时），没有常驻进程、没有连接复用；Pillow 兜底则逐字测量宽度。
- **头像下载是同步 `urllib.request.urlopen`**（`account_cards.py:1175-1186`、`:769-792`），发生在持锁的渲染线程里：一个头像 5s 超时 × 若干头像，会拖住所有卡片渲染；也占用线程池线程（阻塞 IO 本应交由 aiohttp）。
- **Pillow 文本布局近似 O(n²)**：`wrap()` 对每个候选字符调用 `_tracked_width()`，后者又对串内每个字素调用两次 `textbbox`（`output_renderer.py:56-63, 472-491`）。一行 100 字 ≈ 5000+ 次字体测量；长消息兜底和卡片 Pillow fallback 在无浏览器环境会明显变慢。
- 图片缓存按内容摘要命中，设计是对的；但**全局锁让“缓存未命中”的并发请求互相阻塞**，缓存命中也先抢锁再判断（小问题，但可优化）。

### B5. 重型解析/聚合在事件循环里同步执行

**位置**：`src/account_fetcher.py` 各 `_parse_cf_*`、`_build_cf_analysis`、`_fetch_atcoder_analysis`、`_fetch_nowcoder_analysis` 等。

- 这些函数在 async 协程内直接跑 CPU 密集循环（对最多 10000 条提交逐条正则/`_parse_int`、两次以上全量遍历），没有 `to_thread`。单用户约 0.1~1s；AstrBot 是单事件循环，**这个时间内整个机器人（含其他插件）都会卡顿**。8 路并发抓取时每个 CPU 片段仍然阻塞循环。
- 牛客练习页解析（20 页 × 正则提取）和 AtCoder 1 万条提交的统计同理。

### B6. 牛客/AtCoder 详情分析存在“请求数爆炸”

- **牛客**：`_fetch_nowcoder_problem_metadata`（`account_fetcher.py:1306-1355`）对每个去重通过的题目单独发一次 `problem/list?keyword=ID` 请求，上限 300 题 → **冷缓存时一个用户最多 300 次 HTTP**（并发 6）。即使有全局题目元数据缓存，首个“我的牛客”仍可能十几秒到几十秒。
- **AtCoder**：提交记录按 `from_second` 逐页串行拉取（`account_fetcher.py:2228-2266`），500 条/页，最多 20 页串行；`problem-models.json` 是一次性大资源（24h 缓存，合理）。
- 这些都被 `_analysis_semaphore=2` 限制并发，避免打爆平台，但**冷启动延迟高**。

### B7. 定时任务/配置读取的重复 KV 流量

- **`reminded` 去重表**：`src/scheduler.py:87-115` 每个 tick 对每个群都 `get_kv_data("reminded")` 读回整个列表，每推送一次就整体排序并整块写回（上限 2000 条）。群多 + tick 30s → 每 30s 多次 O(K) 读写。
- **`get_settings()` 高频重复读**：`main.py` 中 `_adaptive_results`、`_post_to_group`、`send_notification` 几乎每个回复/推送都各读一次 KV；`_post_to_group` 短文本也先 `get_settings()`。
- **`_update` 串行刷新**：`main.py:2668-2676` 按平台顺序 `force=True` 抓取，一次 `/update` 的延迟是 5 个平台延迟之和；可以并行（比赛抓取器内部已有并发合并，跨平台也能直接 gather）。

### B8. 次要但真实的问题

- **内存缓存无淘汰**：`AccountFetcher._cache` / `_locks`（`account_fetcher.py:284-291`）与 `_nowcoder_problem_cache`（`:295-297`）只增不减，长运行进程内存随用户/题目数增长，重启才释放。排行 `_rank_cache` 有 64 条上限，这块反而是好的。
- **比赛持久化缓存写放大**：`contest_fetcher.py:201, 319-356` 每次抓完一个平台就整体重写 `contest_cache.json`；`_update` 串行抓 5 平台 = 5 次全量写。
- **`get_profiles` 非 CF 路径无并发上限**（`account_fetcher.py:433-446`），当前调用方通过 `_rank_fetch_semaphore(8)` 限制了，但接口本身不设防，若将来被别处直接调用会瞬时全量并发。

## 三、优化方向（均不改变功能）

> 优先级说明：**P0 = 立竿见影且风险低 / P1 = 收益大但改动面稍大 / P2 = 锦上添花**。每项都给出“问题 → 方案 → 预期收益 → 兼容性”。

### P0-1 排行计算去“详情化”：进步榜改为摘要 + 快照，不再逐人抓重型详情

- **问题**：progress 模式 `detail=True`（`main.py:1756`）导致 CF 每人 3 次请求且被全局锁串行（B1、B2）。
- **方案**：
  1. 排行/进步榜一律使用**摘要资料**（`detail=False`，CF 走批量 `user.info`），Rating 值直接来自摘要；
  2. 近 7 日变化优先取 `rating_delta_for_period(profile)`（CF 摘要无历史时）→ **快照表 `get_weekly_deltas`**，快照在每次非只读排行时已批量写入（现有逻辑保留）；
  3. progress 模式下不再调用 `get_profile(detail=True)`；仅在快照缺失的成员上做“按需补详情”的后台预热。
- **收益**：CF 进步榜网络请求从 `3N` 降为约 `N/50` 次批量 info；200 人进步榜从“分钟级”降为秒级；牛客/洛谷/AtCoder 不再为进步榜抓分析数据。
- **兼容性**：展示字段不变（Rating 与近 7 日变化均来自现有模型字段）。

### P0-2 CF 详情请求去串行化：摘要优先 + 后台预热 + 全局锁细粒度

- **问题**：B1 的 2.1s 全局锁 + 单 handle 详情请求。
- **方案**：
  1. `我的cf` / 群排行等先立即返回**摘要 + 缓存详情**（现有 10 分钟/12 小时缓存），把 `user.rating`、`user.status` 的拉取放到**后台任务预热**，用户首屏不等网络；
  2. 锁粒度从“所有 CF 请求”拆成“同一 handle 的详情请求”锁；`user.info` 批量不受 2.1s 限制约束（CF 对 `user.info` 限速宽松，可保留小间隔但不再与 rating/status 共用同一把锁；
  3. 若保留全局限速，则把 2.1s 改为“最少间隔 + 批请求合并等待”，利用等待时间并行发起其他平台请求，而不是空睡。
- **收益**：CF 相关命令的冷启动延迟从 6s+ 降到 <1.5s（摘要返回），并发查询不再互相排队。
- **兼容性**：对外 API 不变；限速仍保留，只是更细粒度，降低被 CF 封禁风险的同时提升吞吐。

### P0-3 排行缓存键去掉 `record_metrics`，单次计算同时服务“榜单”与“个人名次”

- **问题**：B2 的 `record_metrics` 导致同群同平台重复计算。
- **方案**：把“记录快照”改为计算的**副作用**（同一次 `_collect_rank_rows_uncached` 完成抓取、排行、快照写入），缓存键只保留 `(group, platform, progress)`；
- 个人“本群第 N 名”改为**读取同一份 5 分钟短缓存**或一个“平台 → 已排序用户表”的全局榜单（`user_id -> rank` 索引在内存中构建），不再为单人名次触发全量群排行。
- **收益**：“我的战绩@群”从 O(整群全平台抓取) 降为 O(1) 缓存命中；群排行多指令并发时只算一次。
- **兼容性**：功能与展示完全一致。

### P0-4 `_update` 与“群排行总览”的平台循环并行化

- **问题**：`main.py:2005-2020`（总览逐平台串行）、`main.py:2668-2676`（update 逐平台串行）。
- **方案**：两处都改为 `asyncio.gather` 并发抓取/计算（平台间无依赖；在线平台内部已有单平台合并锁，并发安全）。
- **收益**：`/update` 延迟从 Σ延迟 → max 延迟（通常减少 3~4 倍）；`群排行`总览同理。
- **兼容性**：零风险，纯编排改动。

### P1-1 KV 整表读改写 → 内存态 + 按用户分片 / 延迟落盘

- **问题**：B3。
- **方案**（可组合）：
  1. **内存态主副本**：启动时把 `accounts`、`group_rank_members`、`settings`、`groups` 一次载入内存，运行期读写内存，变更后**整对象异步/延迟写回 KV**（保持 KV 作为持久层），WebUI 与其他入口写 KV 时做内存失效；
  2. **快照分片**：把 `account_rating_snapshots` 从“一张大表”改为“每用户一个 KV 键”（`snapshots:<user_id>`），写入只影响单个用户；读取 `get_weekly_deltas` 改为按批并行读分片；
  3. **快照 TTL/压缩**：只保留“近 90 天 + 每周一个采样”或减少到 30 条，写入前按用户懒压缩。
- **收益**：排行/绑定的 KV 成本从 O(全量) 降为 O(涉及用户)；大群场景延迟显著下降。
- **兼容性**：持久化格式可做迁移（旧键读取 + 新键写入），不改变任何用户可见行为。若不想动存储格式，**只加内存缓存 + 延迟写回**即可获得大部分收益。

### P1-2 渲染架构：单飞锁 + 有界并发 + 浏览器复用 + 头像异步预取

- **问题**：B4。
- **方案**：
  1. **按内容摘分锁**：把全局锁换成 `dict[digest] -> Lock`（单飞，同内容只渲染一次），不同内容之间用**有界信号量（如 2~4）**控制并发，避免排队互斥；缓存命中路径**先无锁检查**返回；
  2. **浏览器常驻/复用**：用一次性的 headless 调试端口（`--remote-debugging-port` + CDP `Page.captureScreenshot`）或至少把 `subprocess` 换成可复用的渲染进程池；若受环境限制，则通过**多级渲染队列**把“渲染任务”与“图片缓存”解耦：先回文字/旧缓存，后台生成新图（异步刷新缓存）；
  3. **头像下载移出渲染锁**：用 `aiohttp` 在 `async` 层预下载到本地头像缓存（现有 `avatars/` 目录已存在），渲染线程只读本地文件；无本地缓存时先用占位头像并后台补齐；
  4. **Pillow 布局优化**：`wrap` 改为“按宽度前缀和的二分查找”或维护增量宽度，`_tracked_width` 用 `font.getlength` 一次性测量缓存到行级，避免每字符两次 `textbbox`；卡片模板同理。
- **收益**：多群同时查询不再互相排队；卡片生成延迟从“秒级+排队”降到“秒级单张”；头像慢速不再阻塞他人；无浏览器环境下长消息兜底提速数倍。
- **兼容性**：渲染产物（PNG/文字兜底）完全不变。

### P1-3 重型解析移出事件循环，并原子化缓存

- **问题**：B5。
- **方案**：
  1. 把 `_parse_cf_difficulty_distribution`、`_build_cf_analysis`、牛客分页解析、AtCoder 统计等 CPU 密集函数用 `asyncio.to_thread` / `run_in_executor` 执行（解析输入是一次性取回的原始文本/JSON，无共享状态，线程安全）；
  2. 同时把**解析结果缓存**移到“原始响应文本缓存”之前：优先缓存**已结构化 profile/analysis**（现有内存缓存已做），再考虑把原始文本缓存为磁盘 LRU，避免重启后重抓重解析。
- **收益**：机器人事件循环不再被 0.1~1s 级 CPU 块卡顿（连带保护其他插件）；批量排行时整体吞吐提升。
- **兼容性**：纯内部改动。

### P1-4 牛客题目元数据改批量接口 / AtCoder 分页并行

- **问题**：B6。
- **方案**：
  1. 牛客：调研 `problem/list` 是否支持无关键词分页拉取（或用现有 practice 页内嵌的难度/标签字段），把“每题目 1 请求”改为“**一次列表页分页扫描**”，内存 LRU 保持全局共享；无法改接口时至少把 300 上限调低并做**磁盘持久化**（当前重启即丢）。
  2. AtCoder：`from_second` 分页虽然依赖顺序，但可以**按天分桶并行**（例如按最近 30/90/180 天并行为期窗口拉取，各窗口独立 `from_second`）后合并去重；或者保留串行但**提高 page size 上限**（API 上限 500 时，改为并发 3~4 个时间窗口）。
- **收益**：冷缓存“我的战绩”从“几十秒”降到“秒级”；降低对平台请求压力（对平台更友好）。
- **兼容性**：数据来源不变。

### P2-1 定时任务去重表与配置读取缓存

- **方案**：
  1. `reminded` 改为**内存集合 + 定期整写**（启动时加载，每次提醒只写增量或按 N 秒批量落盘）；或按“群键分片”（`reminded:<group_id>`），避免每 tick 读全表、每提醒写全表；
  2. `get_settings()` / `get_groups()` 结果在内存缓存 30~60s（或由 WebUI 保存接口主动失效），`_post_to_group` 不再每次读 KV。
- **收益**：30s tick 的 KV 流量和提醒写入从 O(群×K) 降为 O(群)；推送路径延迟下降。
- **兼容性**：零功能变化。

### P2-2 比赛持久化缓存写放大收敛

- **方案**：`_save_persistent_cache` 加**防抖（debounce）**：多个平台抓取完成后 2~5s 内合并写一次；或用内存脏标记，进程 `terminate()` 时统一落盘。
- **收益**：`/update` 从 5 次全量写 → 1 次；长期运行减少磁盘 IO。
- **兼容性**：无功能影响。

### P2-3 内存缓存加 TTL 淘汰，杜绝无界增长

- **方案**：给 `AccountFetcher._cache` / `_locks` / `_nowcoder_problem_cache` 加“过期扫描 + 上限（如 LRU 1 万条）”；`_fetch_locks` 在对应项无等待者时清理。
- **收益**：长运行内存稳定，避免大群/多平台长期使用后 OOM 前兆。
- **兼容性**：纯内部。

## 五、建议实施顺序

1. **P0-1 + P0-3**：排行去详情化、缓存键去 `record_metrics` —— 改动集中在 `main.py`，收益最大、功能不动；
2. **P0-2 + P0-4**：CF 锁细粒度/后台预热、平台循环并行 —— 提升冷启动与 `/update`；
3. **P1-1**：KV 内存化/分片 —— 解决规模增长后的存储放大；
4. **P1-2**：渲染单飞锁 + 浏览器复用 + 头像异步化 —— 解决多群并发体验；
5. **P1-3 / P1-4**：CPU 解析出事件循环、牛客/AtCoder 请求降量 —— 消除卡顿与冷启动长尾；
6. **P2 系列**：定时任务 KV 优化、持久化缓存防抖、缓存 TTL —— 长期稳定性。

所有方向均可在不改动指令、数据源、展示格式、WebUI 的前提下实施；优先做 P0 项后即可获得大部分收益。
